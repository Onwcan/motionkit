# ADR-0004: CI compiles a downstream consumer against the installed package

- **Status**: Accepted
- **Date**: 2026-08-25
- **Deciders**: Onur Can Urhan

## Context

`motionkit` is a library. Its contract with the outside world is not only the
headers — it is also the CMake package: `find_package(motionkit)` must succeed,
and the target it defines must have the name consumers were told to use.

That contract is invisible to unit tests. Every test in this repository links
against the in-tree target, where an `ALIAS` makes `motionkit::core` available.
The installed package is generated by a different mechanism entirely
(`install(EXPORT ...)` plus `NAMESPACE`), and nothing forces the two names to
agree.

## The failure this caught

On the first run of the install path, the exported target was
`motionkit::motionkit_core` — namespace plus raw target name — while every
consumer, the README and the in-tree alias all used `motionkit::core`. A
downstream `find_package(motionkit REQUIRED)` followed by
`target_link_libraries(app PRIVATE motionkit::core)` failed at configure time
with "target not found".

All 54 unit tests passed while this was broken. They could not have caught it:
they never touch the installed tree.

The fix was `EXPORT_NAME core` on the target. The value here is not the fix —
it is that the bug surfaced in under a minute instead of in a downstream
project weeks later, where it would have looked like the consumer's fault.

## Decision

CI runs an `install-consumer` job that:

1. Configures with `MOTIONKIT_BUILD_TESTS=OFF`, then builds and installs the
   package into a staging prefix.
2. Generates a fresh, minimal CMake project that has never seen the source tree.
3. Configures it with `CMAKE_PREFIX_PATH` pointing at the staging prefix, using
   only `find_package(motionkit REQUIRED)` and the public target name.
4. Compiles it, **and runs the resulting binary**.

Step 4 matters: a package can configure and link correctly and still ship
headers that do not match the installed library.
The consumer uses explicit failure return codes rather than `assert`, because
the Release build disables assertions.

The consumer deliberately uses the public include and CMake target published in
the README. If the documented `find_package` and link contract stops working,
CI fails.

The consumer does not set `CMAKE_CXX_STANDARD`, and it includes the frame-graph
API whose defaulted comparison requires C++20. The installed `motionkit::core`
target propagates its `cxx_std_20` requirement, so the package must put a
downstream compiler into a compatible language mode itself.

Disabling the repository tests is part of the boundary, not an optimisation.
Top-level motionkit builds enable tests by default, which would fetch GoogleTest
and compile test-only instrumentation before the installed package is exercised.
Those checks belong to the build-and-test jobs. The install-consumer job should
fail only when building, installing or consuming the package fails.

## Consequences

**Positive**

- The public CMake contract is tested, not assumed.
- Header install coverage is checked implicitly — a header omitted from
  `install(DIRECTORY ...)` fails this job and nothing else.
- The documented usage example cannot silently rot.
- Test-only dependencies and instrumentation cannot make the package-consumer
  gate fail before it reaches the installed artifact.

**Negative**

- One extra CI job, roughly a full clean build. Acceptable for a library this
  size; if build time becomes a problem the job can be restricted to `main` and
  release tags rather than every pull request.

**Follow-on**

This generalises. When WP-07 defines the versioned service contract, the same
idea applies one level up: build a **v1** client and run it against a **v2**
server in CI. Backward compatibility, like package export, is a property that
only a real consumer can verify — which is precisely what the requisition means
by "versioning strategies and backward compatibility management".
